# Pradeep Maurya — Portfolio

Static HTML/CSS/JS — no build step needed to *view* it, no framework, no CDN calls.
Everything (fonts, GSAP, Lenis) is served from `assets/`, so it works offline and
can be dropped on any static host.

## Run it

Open `index.html` directly, or serve the folder (recommended — some browsers
restrict fonts over `file://`):

```sh
python serve.py          # http://localhost:8000
```

Use `serve.py`, not `python -m http.server`. The plain server ignores
`_headers` and `.htaccess`, so locally you get no `Link` response headers and
no `Accept: text/markdown` negotiation — the site looks broken to any
agent-readiness scanner even though the deployed config is correct.
`serve.py` applies both, so local matches production.

## Editing content

**Don't edit the `.html` files by hand** — they're generated. Edit the data blocks
at the top of `build.py` (`ME`, `NAV`, `PROJECTS`, `SKILL_GROUPS`, `EXPERIENCE`,
`CREDENTIALS`, `STATS`, `CAPABILITIES`), then:

```sh
python build.py
```

That regenerates all 15 pages with a consistent header, menu, footer and meta tags,
plus `sitemap.xml` and `robots.txt`.

## Link relations (RFC 8288)

Defined once in `SITE_RELS` in `build.py` and emitted two ways:

- **`<link>` elements** in every page head — work on any host, including
  GitHub Pages, which can't set custom headers at all.
- **An HTTP `Link:` response header** — needs server config, generated into
  `_headers` (Netlify, Cloudflare Pages) and `.htaccess` (Apache).

Only relations in the IANA registry that are actually true of this site are
included: `author`, `me` (×3), `privacy-policy`, `terms-of-service`, plus a
per-page `canonical`. `api-catalog` and `service-doc` are deliberately absent —
there's no API behind a static portfolio, so they'd point agents at a 404.

Other hosts — copy the value from `_headers`:

```nginx
# nginx
add_header Link '</about.html>; rel="author", ...' always;
```

```json
// vercel.json
{ "headers": [{ "source": "/(.*)", "headers": [
    { "key": "Link", "value": "</about.html>; rel=\"author\", ..." } ] }] }
```

GitHub Pages can't send custom headers — the `<link>` elements are the fallback
there.

## Markdown for agents

Every page has a `.md` twin (`about.html` → `about.md`), generated by
`markdown_page()` in `build.py` from the same data as the HTML — not converted
from it, so there's no nav/footer noise. Each page advertises its twin:

```html
<link rel="alternate" type="text/markdown" href="/about.md">
```

and the same relation ships as a `Link:` header per page in `_headers`.

**Serving markdown on `Accept: text/markdown`** — HTML stays the default:

| Host | What to do |
| --- | --- |
| Cloudflare (proxied) | Nothing here — turn on **Rules → Settings → Markdown for Agents** in the dashboard |
| Apache | Already done: `.htaccess` rewrites to the `.md` twin when `Accept` matches |
| Netlify / Cloudflare Pages | `_headers` sets the content type; add an edge function using `markdown-for-agents.worker.js` |
| Vercel (this site) | Already done: `vercel.json` sets headers and rewrites |
| Workers | Deploy `markdown-for-agents.worker.js` |

The negotiation compares q-values, so `text/markdown;q=0.5,text/html;q=0.9`
still gets HTML. `Vary: Accept` is set on both forms so a cache can't replay a
markdown body to a browser.

## llms.txt

Two files at the root, generated from the same data as everything else:

| File | What it is |
| --- | --- |
| `llms.txt` | Curated index per [llmstxt.org](https://llmstxt.org) — H1, blockquote summary, then `## Core` / `## Projects` / `## Optional` link sections. Links point at the `.md` twins, so a model following one gets clean text with no second hop. |
| `llms-full.txt` | Every twin inlined — the whole site in one fetch, ~5.5k tokens. |

Items under `## Optional` are the ones a model can skip when context is tight,
which is what that heading means in the spec.

Both are markdown-formatted but `.txt` by convention, and both are served as
`text/plain; charset=utf-8` — the charset is explicit because the content
carries em dashes and "Résumé".

## Content Signals

`robots.txt` declares how you'd prefer the content to be used, via
[Content Signals](https://contentsignals.org/). Edit `CONTENT_SIGNALS` in
`build.py` and rebuild:

```python
CONTENT_SIGNALS = {"search": "yes", "ai-input": "yes", "ai-train": "no"}
```

| Signal | Set to | Why |
| --- | --- | --- |
| `search` | `yes` | The site exists to be found. |
| `ai-input` | `yes` | It ships `llms.txt` and serves markdown on `Accept: text/markdown` *specifically* so assistants can read it. `no` would contradict that. |
| `ai-train` | `no` | No reciprocal benefit, so withheld. |

These are preferences, not access controls — they tell well-behaved crawlers
what you want and nothing more. Flip `ai-input` to `no` if you'd rather
assistants didn't quote the site in answers, but then the `llms.txt` and
markdown-for-agents work is sending the opposite message.

## API

Two Vercel serverless functions in `api/`, described for machine discovery.

| Endpoint | Purpose |
| --- | --- |
| `POST /api/contact` | Delivers the contact form via Resend |
| `GET /api/health` | Liveness + whether mail sending is configured |

Discovery documents, all generated by `build.py`:

- `/.well-known/api-catalog` — RFC 9727 catalog as an RFC 9264 linkset
- `/openapi.json` — OpenAPI 3.1 spec
- `/docs/api.html` (+ `.md` twin) — human-readable reference

`SITE_RELS` now includes `api-catalog`, `service-desc` and `service-doc`,
because there is finally something real behind them.

### Setup (required for the form to actually send)

In **Vercel → Project → Settings → Environment Variables**:

| Variable | Required | Notes |
| --- | --- | --- |
| `RESEND_API_KEY` | yes | From [resend.com](https://resend.com) — free tier is ample |
| `CONTACT_TO` | no | Defaults to the address in `api/contact.js` |
| `CONTACT_FROM` | no | Must be a domain verified in Resend. Until `pradeepmaury.in` is verified there, Resend's test sender is used |

Without the key, `/api/contact` returns `503` and the front end falls back to
opening the visitor's mail client — so the form keeps working either way.

### Protections

Honeypot field (`website`), per-field length caps, email format check, method
guard, and provider errors logged server-side but never returned to the client.

## Personal Agent Protocol (Poppy)

`/.well-known/poppy.json` — a **website-only** declaration, which the spec
allows explicitly (`web: {}` with no `auth` block).

Deliberately *not* declaring `agent` or `apis`: either of those obliges you to
publish an `auth.issuer` with matching RFC 8414 metadata, and there's no
authorization server here. The API that exists is public by design, so it has
no issuer to name.

`organization.domain` is the registrable domain `pradeepmaury.in`. The spec
matches it against the requested hostname ignoring a leading `www`, so it
covers both the apex and the `www` host the site actually serves from.

## ARD manifest

`/.well-known/ai-catalog.json` — an [Agentic Resource Discovery](https://agenticresourcediscovery.org/)
manifest listing what this origin offers, generated by `build.py`.

Six entries, each backed by a file the site actually serves: the OpenAPI spec,
the RFC 9727 API catalog, `llms.txt`, `llms-full.txt`, `agent-data.json` and
the sitemap. Every entry carries a `urn:air:pradeepmaury.in:<ns>:<name>` id, an
IANA media type, and 2–5 `representativeQueries` so registries can build
embeddings.

Served with `Access-Control-Allow-Origin: *`, because a registry fetches it
cross-origin and would otherwise be blocked.

**Deliberately absent: an MCP server entry.** The WebMCP tools run in the
visitor's browser — there is no hosted MCP endpoint a registry could call, and
listing one would send agents to a URL that never answers.

> **`specVersion` is set to `"0.1"` and needs confirming** against the
> published spec before this is worth submitting to a registry. Everything
> else in the file is derived from real resources; that one value is the only
> guess.

## WebMCP

`assets/js/webmcp.js` exposes the site's actions to an in-browser AI agent via
[WebMCP](https://webmachinelearning.github.io/webmcp/).

| Tool | Does |
| --- | --- |
| `list_projects` | Projects with stack, year and links; optional technology filter |
| `get_profile` | Name, role, contact, skills, work history |
| `read_page` | Any page as clean markdown; accepts page names or project slugs |
| `send_message` | Posts the contact form — a real email, so the tool description tells the agent to confirm first |

Data comes from `/agent-data.json`, generated by `build.py` from the same
source as the HTML and fetched lazily on first tool use, so a normal page view
pays nothing for it.

The contact form is *also* annotated declaratively (`toolname`,
`tooldescription`, `toolparamdescription`), which is the other half of the
WebMCP spec.

Kept out of `app.js` deliberately: that file returns early when GSAP is
missing, and tool registration shouldn't depend on an animation library. The
API is young, so every call is feature-detected and wrapped — browsers without
it do nothing rather than throwing.

These need a service this site doesn't run. Publishing the metadata anyway
would advertise endpoints that 404, which is worse for an agent than a clean
absence: it burns requests and implies the site's auth or API is broken rather
than absent.

| Item | Requires |

`POST /api/contact` and `GET /api/health` are deliberately public — a contact
form behind OAuth is unusable, and liveness probes are meant to be open.

## Deployment

Live at **https://www.pradeepmaury.in** on **Vercel**.

`SITE_URL` uses the **www** host because Vercel currently 308-redirects
the apex to it. Canonicals must name the host that actually serves the
page — pointing them at a redirect is an SEO smell. To use the shorter
apex instead, make it the primary domain in Vercel → Project → Settings →
Domains, then drop the `www.` from `SITE_URL` and rebuild.

`SITE_URL` at the top of `build.py` drives every absolute URL — sitemap,
canonicals, `llms.txt`, `robots.txt`. Change it there and rebuild; nothing else
needs touching.

**Vercel reads `vercel.json` only.** It ignores `_headers` (Netlify, Cloudflare
Pages) and `.htaccess` (Apache) — both are generated for portability but are
inert here, and are simply served as static files. `vercel.json` carries the
`Link` headers and the `Accept: text/markdown` rewrites.

Caveat on the rewrites: Vercel's `has` condition matches a regex against the
Accept header, so it can't compare q-values the way `markdown-for-agents.worker.js`
does. A client sending `text/markdown;q=0.1` would still get markdown. Browsers
never send `text/markdown` at all, so HTML stays the default where it matters.
Deploy the Worker as middleware if you want strict q-value handling.

The sitemap is derived from the page list, so new pages appear automatically —
`404.html` is excluded, and `index.html` is listed as the bare root (`/`) so it
doesn't compete with `/index.html` as a duplicate.

## Artwork

### Portrait

`assets/img/portrait.jpg` (900×900, About hero) and `assets/img/portrait-pill.jpg`
(720×304, home hero pill) are cut from one source photo. To swap the photo:

```sh
python assets/img/_crop_portrait.py path/to/new-photo.jpg
```

Both boxes use `object-fit: cover`, so the script crops to the exact display ratio
and the browser never crops again. If the new photo frames the subject differently,
adjust `FACE_X` / `SQUARE_Y` / `PILL_Y` at the top of that script — they're
fractions of the image, not pixels.

### Favicons

The PM monogram set — `favicon.ico` (16/32/48), `favicon.svg`,
`apple-touch-icon.png` (180), `icon-192.png`, `icon-512.png`:

```sh
python assets/img/_favicons.py
```

It draws the tile in a headless Chrome so the monogram uses the site's own
Archivo webfont — a favicon renders outside the page, so an SVG's
`font-family` never resolves and would fall back to Arial. Chrome is located
automatically; override with the `CHROME` environment variable.

The tile is accent-filled rather than the site's dark-with-hairline logo: at
16px a hairline disappears and a dark tile vanishes into dark browser chrome.

### Project covers

Three projects use real screenshots (`.jpg`), two still use generated
placeholders (`.svg`). `build.py` picks the right file per project via the
`SCREENSHOTS` set and the `cover()` helper — add a slug there when you swap one.

**Real screenshots** — take a browser screenshot, drop it in
`~/Pictures/Screenshots`, add an entry to `SHOTS` in the script, then:

```sh
python assets/img/_frame_screenshot.py            # all
python assets/img/_frame_screenshot.py consentx   # just one
```

It crops the browser's own toolbar off the top (`chrome_px` per entry — the
pixel row where the page actually starts) and sits the page in a neutral window
frame on the same dark canvas the generated covers use. Output is 2560×1600.

**Placeholders** for projects without a screenshot yet:

```sh
python assets/img/_generate.py
```

Either way the cover is **16:10**. The index row and spotlight figure crop to
16:9, so keep ~200px of breathing room top and bottom; the project-page hero
crops to a square, so expect the centre to be what shows there.
